# V6 实现、自动运行与仍未解决的问题

2026-11-21 的两轮运行均只输入原论文网址，自动关联源码、固定版本、取证、抽取和复核。没有输入人工整理的权限、旧提案、参考答案或复现结论。以下是已知开发案例的能力测试，不是盲测准确率；两轮分开统计。

## 实现变化

1. `input_channels.py`分别发现问题、文档、标签和反馈输入；一条文档信息流不能替代同一调用的问题信息流。
2. `data_witnesses.py`取得代码/配置实际引用的数据文件，验证固定原文和对象身份，只向模型提供有界原文记录。采样不能支持全体不存在的结论。
3. `declared_contract.py`先只读论文，抽取知识限制、任务组成、适用范围和构造过程；输出保持未受信任。随后映射源码、独立复核，仍必须引用原论文，不能靠提案本身产生`allow/deny`。
4. `repair_guard.py`拒绝非法编号、未知目标和重复引用选择，保留未验证指针，继续复核其他证据；不会猜编号或改分类。
5. 部署时必要输入的来源/迁移问题单列为`deployment_findings`，不把“来源未建立”直接当成`deny`。PDF换行的官方仓库链接识别也已修复。

原Notion五元信息流与固定范围仍是底层比较对象，详见[对应关系](NOTION_MODEL_MAPPING_ZH.md)及[V6方法](AUTOMATIC_V6_ZH.md)。

## 如何理解当前效果

目前自动流程已重新检出ASPI的限定发现，但**尚未完整恢复我们人工对ObliInjection的发现**。后者现在缺的是论文概念、知识限制与具体问题字段的语义对应，不能再归因于源码没下载或问题输入没找到。MUZZLE本轮取得了含PAIR代码的106个源码段，但没有成功完成独立复核；已有自动提案不作为最终发现。

两轮都没有经认证的论文级negative。单条怀疑被许可反驳，不代表整篇阴性。历史论文和旧回归仍保留；本次没有把所有历史论文重新跑一遍。

请求后端为现有ChatGPT登录的Codex CLI，固定请求`gpt-6.1-sol`，无模型替换或API后备。CLI事件没有提供可验证的实际服务模型ID，因此报告保留`actual_model=null`；部分失败调用没有完整usage，不能解释为零使用。没有执行作者攻击代码或重跑ASR。

软件检查为509项通过，覆盖来源验证、信息流/实例门禁、数据摘录、引用恢复与重放隔离；该数字不是论文检测准确率。原始输出和日志保留在本地，公开报告提供安全投影及原产物hash，不包含完整论文、源码、原始数据或私人绝对路径。

## 复现入口

在仓库根目录运行，输出仍是一篇一个结果；目录省略时自动生成：

```bash
python3 -B scan.py https://arxiv.org/pdf/2605.17324v1 \
  --model gpt-6.1-sol --max-calls 4 --source-fetch files --require-source

python3 -B scan.py https://arxiv.org/pdf/2512.09321v3 \
  --model gpt-6.1-sol --max-calls 4 --source-fetch files --require-source

python3 -B -m unittest discover -s tests -q
```

前两条会产生新的账户模型用量，且结果可能受模型抽取变化及上游版本变化影响。历史结果由各自冻结输入、代码hash和调用账本约束；新运行不能覆盖旧输出。
