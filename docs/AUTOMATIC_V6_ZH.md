# V6：按输入通道审计，读取有界数据证据，单列部署来源问题

输入仍任选一个：

```bash
python3 -B scan.py /path/to/paper.pdf
python3 -B scan.py https://arxiv.org/abs/2605.17324v1
```

普通使用无需填写仓库、权限、信息流或参考答案。CLI与批量入口默认V6；历史V4/V5可用`--engine-version 4/5`重放。Python库函数保留原兼容默认，新调用应显式传入`engine_version=6`。

V6源码审计现在先调用一次模型，只输入论文，抽取声明、任务组成与构造过程；再做论文＋源码映射、独立复核。新运行至少需要3次调用，有引用修复时最多4次：

```bash
python3 -B scan.py PAPER_URL --model gpt-6.1-sol --max-calls 4
```

只准备输入不调用模型。历史提案不补跑第一阶段；需要重放带声明提案的新输出时，额外用`--declared-contract <原输出中的declared_contract.json>`保留同一输入绑定。这个参数用于重放，普通审计自动生成。

## 0. 先从论文独立建立声明模型

`declared_contract.py`的第一阶段只看到论文原文，不含源码、人工发现、标签或旧结果。它把角色、阶段、来源、许可/禁止的知识精度、适用范围、例外、任务组成及构造步骤分别记录。

\[
\widehat\Gamma=\operatorname{Extract}_{paper}(P),\qquad
\widehat D=\operatorname{Map}(P,C,\widehat\Gamma),\qquad
R=\operatorname{Gate}(P,C,\widehat D,\operatorname{Review}(P,C,\widehat D)).
\]

其中两个带帽对象都只是模型提案。`declared_contract_proposal`不直接进入许可判定；后续映射和独立复核必须重新引用论文原文，检查术语定义和信息组成与代码参数的语义关系。代码中同名变量不自动等于论文概念，论文说基于元数据生成内容也不自动意味着禁止某项知识。含混声明继续保留为含混。

第一阶段的引文、原始论文hash与验证结果一并保存，并纳入后续输入hash。精确定位只证明引文存在，不能代替语义复核；未定位的提案不会变成论文证据。

代码来源识别也支持PDF中`https://github.com/`与下一行owner/repo分开的情况：须有明确的作者代码可用性上下文，并与同页完整链接注释精确对应；单独的GitHub主机、跨段文字或相关工作链接不能据此认作作者实现。

## 1. 原来的判定规则保留

仍比较同一五元信息流和固定范围中的声明与实现：

\[
A(e,\sigma)\land(\Gamma_{decl}\vdash deny(e))
\land(D_{impl}\models present(e))\Rightarrow R(e,\sigma)=inconsistent.
\]

候选输入、数据字段存在、未找到线上获取路径，都不会自行生成`deny`或`present`。角色、政策适用、必要实例、实际输入边界与反证仍由V5原有门禁处理。静态条件下的发布实现差异不等于作者历史运行或ASR变化。

## 2. 分别检查问题、文档、标签和反馈

`input_channels.py`从提供的Python源码中静态发现生成/优化/模型调用的输入，跟踪有限深度的赋值、导入函数和同类方法转发。问题、任务、文档、标签、反馈与其他输入分别列成候选；日志、配置项、模型名称和普通工具调用不会仅因名称含target/task就被当成攻击输入。

这些候选是有界、可能出错的取证提示，不是程序语义证明。V6的抽取与独立复核须逐项说明：由哪条信息流覆盖、有什么证据排除，或仍未审清。每个覆盖项需要同时满足：

- 候选来源和接收边界的精确引用通过验收；
- 该来源与边界也出现在对应信息流的实际证据路径中；
- 独立复核支持这一语义对应，且信息表示不混淆，例如文档流不能代替问题流；
- 对应信息流的交付路径验收通过。

候选缺失、限额、解析失败或未支持语言会明确记录。当前上限48项、160个文件、100万源码字符、12万个AST节点、5层追踪。无论是否触及限额，都不能据此认证任意程序的全局信息流。

## 3. 大数据文件读取原文样本

V6显式选择`directed-evidence-v3`取材策略。代码/配置确实引用的JSON可以读取完整、固定版本的原始blob并验证SHA256与Git对象/树身份，再选取有界的原文记录。不会执行上游代码，也不会因数据里的路径、schema指令或文字要求继续取文件。

默认最多8个文件、每文件4MiB、合计8MiB；每文件最多4条记录、每记录32KiB、每文件输出32KiB、总摘录128KiB。记录指针也有限额。畸形JSON、重复键、凭据样式内容、超限和缺失文件均单独记录。

模型只看到精确原文摘录与简洁元数据。完整raw base64留在本地溯源材料中；每条摘录保留原文件hash、记录指针、原始行号及字符/字节范围。重新计算外层hash也不能把改写的摘录、偏移或采样覆盖信息变成有效原文证据。

`shadow/train/test`文件名不证明合成来源或实例分离。问题字段与文档字段须分别审查；若配置和完整索引/ID链证明构造使用同一评估记录，即使语料是合成的，也不能自动当作另一实例的许可。样本可以支持限定的存在性发现，不能证明未展示记录都没有问题。

## 4. 部署来源问题独立输出

`deployment_findings.py`为另一个问题保留位置：论文的部署/迁移主张，需要什么构造输入，以及该输入如何取得。每项要有论文主张、构造依赖、必要知识和独立复核；仅凭缺少获取路径不成立。

| 状态 | 含义 |
| --- | --- |
| `supported_gap` | 所列部署范围存在有据的必要输入，其获取/迁移依据仍未建立 |
| `resolved` | 有肯定证据建立了获取途径，或证明该范围不需要该输入 |
| `uncertain` | 部署主张、依赖、范围或证据尚未充分建立 |

这些辅助发现不会改写知识边界的`allow/deny`，也不会把未知来源等同于已确认违规。材料性的未决部署问题会阻止输出宽泛的“范围内已排除”答案；独立成立的局部违规仍保留。

## 5. 每篇仍一个结果，细节不丢失

`inconsistency=true/false/null`保持原三值含义。确认不一致的具体位置在`findings`；未审清输入在`channel_coverage`；部署问题在`deployment_assessment.findings`。阴性要求原有非空怀疑的证明义务闭合，并通过新增的输入覆盖及部署检查；任何单条确认不一致仍足以报告限定发现。

引用恢复覆盖新增数组字段，但仍只选择同一证据域中的可定位引用，不改分类字段；恢复后需独立复核。V6遇到非法候选编号、未知目标或重复目标时，拒绝相应选择并保留原未验证引用；不会删字、模糊匹配或猜测候选。有效的其他选择可继续验收，输出记录拒绝原因。结构畸形或预备候选被改动仍是技术失败。

旧输出、失败尝试和模型调用账本保留。软件测试、规则重放、已知开发论文测试和独立评估须分开统计，不用程序测试通过数代替检测准确率。
