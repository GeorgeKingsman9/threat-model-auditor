# 三类规则的实现与原网址自动测试

本次普通输入仍只有论文PDF或网址。运行过程不读取人工案例、审定权限、参考标签或旧审计提案。手工研究发现只用于开发规则和运行结束后的对照，不回写自动输出。

## 实现了什么

| 类别 | 核心规则 | 实现 |
| --- | --- | --- |
| 知识边界违规 | 同一范围中适用的禁止＋确认到达匹配的攻击接收者 | 保留V5/V6门禁，V7作为独立类别汇总 |
| 构造契约差异 | 明确的构造／输入来源声明，与同范围发布代码存在经复核的不相容来源 | `construction_contracts.py`；要求语义映射、交付链、必要实例及例外验收 |
| 任务获取／部署假设缺口 | 声明场景与实际任务依赖之间，有材料性的获取、时序或实例衔接缺口 | `deployment_v7.py`；不把未知获取路径转成`deny`或“不可能获取” |

任一类别有确认项，一篇论文就输出一次`inconsistent`，并列出类型及具体位置。`knowledge_boundary_verdict`另存原轨道结果；不能把构造差异或部署缺口误写成知识越权。公式见[规则说明](AUTOMATIC_V7_ZH.md)，带注释的代码摘录见[代码讲解](CODE_V7_ZH.md)。

复核的输入、提示、schema和hash会保存。发生可重试错误时，至多以完全相同的模型和请求再做一次复核；认证、额度、配置、schema等明确错误不盲目重试。每次均计数，不换模型或API。显式恢复入口只读原自动材料，创建新目录，验证原产物逐字节未变。

## MUZZLE：首轮还漏了什么

首轮取得含PAIR代码的106个源码段，源码固定为`9f3effa1668fa29dcba8f2454e711ddf9ef3c038`。自动提案确认原任务信息到达PAIR攻击构造，但第三类别只留下未解决的文字说明，没有结构化来源候选。

审查发现两个需要区分的问题：论文在Zoo中做实验，属于**实验地点**；这不能独自把另行声明的线上执行收窄为`offline_only`。同样，提出任务获取义务不要求先证明未知任务上的成功定理；确认缺口也不能只因为没有这个定理。

另一方面，`explorer.py:777–811`确实在PAIR调用之前取得benign trace，Q可能在允许观察的同实例信息中可见。不能为了匹配既有发现，把这个反证选项删掉。应追查实际上游任务来源、首次可见时点、后续接收时点和对应线上范围，再独立复核。

## 如何复现普通入口

在仓库根目录运行；默认自动生成新输出目录：

```bash
python3 -B scan.py https://arxiv.org/pdf/2512.09321v3 \
  --model gpt-6.1-sol --max-calls 6 --source-fetch files --require-source

python3 -B scan.py https://www.usenix.org/system/files/usenixsecurity26-syros.pdf \
  --model gpt-6.1-sol --max-calls 6 --source-fetch files --require-source

python3 -B -m unittest discover -s tests -q
```

前两条会产生新的账户模型用量。每轮运行受其冻结代码、输入hash、提示和调用账本约束；模型抽取及上游变动可能使新运行不同。原始论文、源码和完整数据保留在本地材料中，公开报告提供安全投影与原产物hash。

这些是两篇已知开发案例的运行，不能视为盲测准确率或泛化能力估计。合成软件测试核验正、反及未确定门禁，不等于本轮测试了真实论文阴性；本轮没有认证的论文级negative。没有执行作者攻击代码或重新运行ASR。
